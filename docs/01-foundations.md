# 01 — 서비스 유형과 PAIS 3.0 구성

[← 목차로](../README.md)

서비스를 만들기 전에 두 가지를 분명히 합니다. 첫째, 만들려는 것이 단일 모델 호출인지, 고정된 RAG인지, 배치 파이프라인인지, 에이전트인지 — 그 차이가 설계와 통제의 무게를 정합니다. 둘째, PAIS 3.0의 어떤 모듈이 각 유형을 지원하는가. 이 문서는 유형의 경계를 구분하고, 모듈 구성을 살핀 뒤, 가장 복잡한 유형인 에이전트의 구성요소를 하나씩 살펴봅니다.

> 본 문서의 수치와 동작은 VCF 9.1.1 / PAIF 9.1.1 / PAIS 3.0 기준입니다(작성 2026-06, 9.1.1과 3.0 GA 반영 2026-09). 2.1 환경에서는 "PAIS 3.0부터"로 표기한 대목만 생략하면 됩니다. 적용 전 최신 공식 문서로 재확인하시기 바랍니다.

---

## 1.1 에이전트 vs RAG vs 워크플로우

세 가지는 자주 혼용되지만 **결정 주체**가 다릅니다.

- **단일 호출** — 입력 한 번, 출력 한 번. 모델은 받은 컨텍스트 안에서만 답합니다.
- **RAG(검색 증강)** — 답하기 전에 지식베이스를 검색해 관련 문서를 컨텍스트로 넣습니다. 단계는 "검색 → 생성"으로 **고정**돼 있습니다. 무엇을 검색할지, 검색을 할지 말지는 사람이 정한 흐름을 따릅니다. (④의 주제)
- **워크플로우** — 여러 단계를 사람이 미리 정한 순서대로 잇습니다. 분기와 반복이 있어도 **처리 순서가 코드에 미리 정해져** 있습니다.
- **에이전트** — 검색할지, 어떤 도구를 부를지, 한 번 더 시도할지, 멈출지를 **모델이 그때그때 판단**합니다. 어떤 단계를 거칠지가 입력마다 달라진다는 것이 핵심 차이입니다.

| 축 | 단일 호출 | RAG | 워크플로우 | 에이전트 |
|----|-----------|-----|-----------|----------|
| 경로 결정 | 없음 | 고정(검색→생성) | 고정(분기 포함) | 모델이 동적 판단 |
| 외부 접근 | 없음 | 지식베이스 | 정해진 도구 | 지식베이스 + 도구(가변) |
| 단계 수 | 1 | 2 | N(고정) | 가변(루프) |
| PAIS 모듈 | Model Runtime | Data Indexing + ④ | (애플리케이션) | Agent Builder |

실무에서는 경계가 섞입니다. PAIS의 에이전트는 **관리형 RAG를 내장한 도구 호출 에이전트**에 가깝습니다 — 지식베이스 검색이 에이전트가 사용할 수 있는 하나의 도구로 노출되고, 거기에 MCP 도구가 더해집니다([09](09-mcp-tools.md)). 단순히 "정해진 답을 검색"하면 충분한 경우라면 에이전트가 아니라 ④의 RAG로 구현하는 편이 단순하고 예측 가능합니다. 이 판단 기준은 [03 설계 패턴](03-design-patterns.md)에서 다룹니다.

위 표가 "누가 경로를 정하는가"의 축이라면, 서비스가 사용자에게 어떤 모습으로 전달되는가의 축이 하나 더 있습니다. 기업이 PAIS로 구축하는 서비스는 대개 다음 네 유형 중 하나이며, 유형마다 어느 모듈을 사용하고 어느 결정이 무거운지가 다릅니다.

| 서비스 유형 | 결정 주체 축에서의 위치 | 핵심 PAIS 모듈 | 무거운 결정 | 대표 예 |
|-------------|--------------------------|----------------|-------------|---------|
| 챗과 Q&A RAG | RAG(고정 경로), 세션이 있으면 Agent Builder의 세션 계층 | Model Runtime, Data Indexing and Retrieval | 데이터 소스 온보딩과 권한 필터, 근거 표시와 폴백 같은 신뢰 UX | 사내 규정과 제품 정보 응대([02 2.6절](02-use-cases.md)) |
| 문서 처리 배치 | 단일 호출의 대량 반복. 사용자 대화 없음 | Model Runtime(임베딩과 완성 엔드포인트) | 온라인 서비스와 GPU를 나눠 사용하는 우선순위와 야간 윈도우, 건당 단가([03 3.7절](03-design-patterns.md)) | 계약서 일괄 요약, 민원 분류, 문서 메타데이터 추출 |
| 임베드 코파일럿 | 단일 호출 또는 RAG를 기존 업무 화면 안에 내장함 | Model Runtime, 필요 시 Data Indexing | 업무 시스템의 사용자 신원을 그대로 전파하는 규약, 기존 시스템과의 연동 | ITSM 화면의 티켓 요약과 답변 초안, ERP 화면의 설명 생성 |
| 에이전트 | 모델이 경로를 동적으로 판단 | Agent Builder, MCP Servers and Tool Gallery, Observability | 자율성 상한([02 2.10절](02-use-cases.md)), 쓰기 작업의 승인, 도구 거버넌스 | 운영 알림 1차 진단([02 2.7절](02-use-cases.md)) |

네 유형은 배타적이지 않습니다. 코파일럿이 내부적으로 RAG를 사용하고, 에이전트가 배치 파이프라인의 결과를 지식베이스로 검색하는 식으로 겹칩니다. 다만 **첫 서비스는 한 유형으로 좁혀** 시작하는 편이 설계와 평가가 단순합니다. 유형이 정해지면 그 유형에 맞는 결정만 무겁게 다루고 나머지는 기본값을 적용합니다.

## 1.2 PAIS 3.0 모듈 구성

PAIS 3.0은 여섯 모듈로 이뤄지며, 에이전트는 이 모듈들을 함께 사용합니다. 모듈 구성은 2.1과 같고, 3.0은 Model Runtime이 모델을 가져오는 방식(공유 모델, 원격 클라우드 모델)과 인증 수단(API 토큰)을 넓혔습니다.

### 1.2.1 모델 계층 — Model Gallery, Model Runtime

- **Model Gallery** — 모델 아티팩트를 담는 저장소로, Harbor(OCI 호환 컨테이너 레지스트리)를 기반으로 합니다. NVIDIA NIM, 자체 모델 등을 프로젝트 단위로 관리합니다. ([10](10-models-serving.md))
- **Model Runtime** — Gallery의 모델을 추론 엔진으로 실행해 **OpenAI 호환 엔드포인트**로 노출합니다. completion(생성)과 embedding(임베딩) 모델을 서빙합니다. 에이전트는 여기서 노출된 completion 엔드포인트를 가져다 사용합니다. 3.0부터는 이 네임스페이스의 GPU에서 실행되는 로컬 모델 외에, 다른 PAIS 인스턴스가 서빙하는 공유 모델과 Google Gemini 같은 원격 클라우드 모델도 같은 엔드포인트 형태로 연결됩니다. 에이전트 쪽에서는 셋 다 드롭다운의 completion 엔드포인트 하나로 보입니다([10 10.1절](10-models-serving.md)).

### 1.2.2 지식 계층 — Data Indexing and Retrieval

데이터소스를 인덱싱해 **지식베이스**로 구성하고, 검색을 제공합니다. 벡터 임베딩은 pgvector 확장을 갖춘 외부 PostgreSQL에 저장됩니다. 에이전트는 지식베이스를 연결해 검색을 수행하며, 검색 자체가 MCP 도구로 노출됩니다(아래 1.2.3). 지식베이스 구성, 청크, 임베딩의 상세는 ④에 위임합니다.

### 1.2.3 도구 계층 — MCP Servers and Tool Gallery (2.1 신규)

Model Context Protocol(MCP)로 외부 시스템을 도구로 연결합니다. PAIS는 MCP를 세 방향으로 다룹니다 — 에이전트가 외부 MCP 도구를 **호출**하고, 지식베이스 검색을 MCP 도구로 **호스팅**하며, 원격 MCP 서버를 도구로 **등록하고 승인**합니다. **Tool Gallery**는 이 MCP 서버들을 중앙에서 관리하는 2.1 신규 기능입니다. ([09](09-mcp-tools.md))

### 1.2.4 조립 계층 — Agent Builder

모델 엔드포인트, 지시문, 지식베이스, 도구, 세션 정책을 조합해 에이전트를 구성하고, **챗 컴플리션 엔드포인트**로 노출합니다. 모델과 지식과 도구 사이의 상호작용을 오케스트레이션하는 것이 Agent Builder의 역할입니다. ([08](08-agent-builder.md))

### 1.2.5 관측 계층 — Observability (2.1 확장)

추론 엔진과 GPU 사용률부터 지식베이스 인덱싱과 에이전트 동작까지 추적합니다. OpenTelemetry 기반 LLM 추적(trace)으로 "사용자 ↔ 모델 ↔ 에이전트 ↔ 지식베이스" 상호작용을 단계별로 확인할 수 있습니다. ([14](14-operations.md))

## 1.3 에이전트의 구성요소

Agent Builder에서 에이전트 하나는 다음 구성요소로 이뤄집니다.

| 구성요소 | 무엇을 정하나 | 출처 모듈 |
|----------|--------------|-----------|
| 모델 엔드포인트(completion) | 추론에 사용할 모델 | Model Runtime |
| 지시문(Instructions) | 시스템 프롬프트와 행동 정책(선택) | Agent Builder |
| 지식베이스(Knowledge Bases) | 검색 대상(선택) | Data Indexing |
| 도구(Tools) | 호출 가능한 MCP 도구 | MCP / Tool Gallery |
| 세션 파라미터 | 대화 이력 길이와 유지 시간(TTL), 요약 전략 | Agent Builder |
| 검색 파라미터 | Top-K, 유사도 컷오프, 인용 표시 | Agent Builder |

이 구성요소들을 어떻게 채우는지가 [08 Agent Builder로 구축](08-agent-builder.md)의 주제입니다. 핵심은 **에이전트가 코드가 아니라 구성으로 정의된다**는 점입니다 — 위저드로 구성하고, 그 결과를 REST API로 소비하며, 구성 코드를 내보내 형상관리할 수 있습니다.

## 1.4 에이전트는 어디서 실행되는가

- **실행 기반** — PAIS는 Supervisor의 vSphere Namespace 안에 프로비저닝되는 **VKS(vSphere Kubernetes Service) 클러스터**에서 동작합니다. Supervisor에 PAIS용 Kubernetes Operator가 배포되고, 관리 파드(API, UI 백엔드, 인덱싱 워커)와 모델 엔드포인트 파드가 VKS 워커 노드에서 실행되며 ESXi 호스트의 GPU에 연결됩니다.
- **노출 형태** — 에이전트는 Model Runtime의 stateless(상태 비저장) 엔드포인트에 **세션, 검색, 도구 호출을 더한 stateful(상태 유지) 계층**으로 동작하며, 챗 컴플리션 엔드포인트로 호출됩니다. (에이전트가 독립된 장기 실행 파드로 배치되는지, Agent Builder 서비스 안의 세션 계층으로 동작하는지는 공식 문서가 단정하지 않으므로, 배포 단위는 적용 환경에서 확인하시기 바랍니다.)
- **GPU 의존** — 모델 엔드포인트는 GPU(또는 2.1부터 llama.cpp로 CPU)에서 추론합니다. 에이전트 자체는 모델과 도구를 오케스트레이션하는 경량 계층이며, 비용의 대부분은 모델 추론(GPU)에서 발생합니다([14](14-operations.md) 비용).

## 1.5 에이전트의 동작 루프

에이전트가 단일 호출과 다른 핵심은 **한 번에 끝내지 않고 스스로 여러 단계를 반복하는** 데 있습니다(1.1절). 한 번의 반복은 대략 다음과 같습니다.

```
사용자 요청 → [ 모델이 다음 행동을 판단 ] → 도구, 검색 호출 → 결과 관찰
                    ^                                              |
                    |______________________________________________|
              (목표를 이룰 때까지, 또는 종료 조건까지 반복)
```

- **판단(계획)** — 모델이 지금 무엇을 할지(검색할지, 어떤 도구를 부를지, 바로 답할지)를 매 단계 정합니다. "생각하고(reason) 행동한다(act)"를 번갈아 하는 이 방식을 흔히 **ReAct** 라 부릅니다.
- **행동** — 정한 도구와 검색을 실제로 호출합니다([09 MCP 도구](09-mcp-tools.md)).
- **관찰** — 그 결과를 컨텍스트에 넣어 다음 판단의 재료로 삼습니다.

이 루프가 에이전트의 힘이자 위험입니다. 경로가 입력마다 달라져 강력하지만, **무한 루프, 같은 도구 반복, 단계 폭주**에 빠질 수 있어 단계 상한과 종료 조건 같은 안전장치가 필수입니다(설계는 [03 3.5절](03-design-patterns.md)). PAIS의 Agent Builder가 내부적으로 정확히 어떤 추론 전략을 사용하는지는 공식 문서로 확인하시고, 여기서는 개념 모델로 이해하시기 바랍니다.

다음 문서는 구현을 다루기 전에 **무엇을, 왜 만드는가** — 어디에 적용해야 성과가 나고 어디서 실패하는지, 위험 등급과 자율성 상한을 어떻게 정하는지 — 를 다룹니다. 그 다음 [03](03-design-patterns.md)에서 구성요소를 **어떻게 조합할지**를 설계 관점에서 다룹니다.
