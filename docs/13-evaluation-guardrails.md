# 13 — 평가와 출시 게이트

[← 목차로](../README.md)

에이전트는 출력이 매번 다르고 경로가 동적이라, 일반 소프트웨어처럼 단언(assertion, '정확히 이 값이어야 한다'는 검사) 방식으로 테스트하기 어렵습니다. 이 문서는 PAIS가 평가에 무엇을 제공하고 무엇은 제공하지 않는지를 분명히 한 뒤, 무엇을 어떻게 측정할지, 어떤 실패 유형을 막을지, 가드레일과 사람 개입을 어디에 둘지를 다루고, 프롬프트를 모델과 같은 1급 자산으로 다루는 수명주기, 릴리스 매니페스트, 출시 심사 패키지로 마무리합니다. 서비스 보안의 준비물과 레드팀 게이트는 [12](12-service-security.md)가 정본이며, 이 문서의 심사 패키지가 그 결과를 담습니다.

> 본 문서의 수치와 동작은 VCF 9.1.1 / PAIF 9.1.1 / PAIS 3.0 기준입니다(작성 2026-06, 9.1.1과 3.0 GA 반영 2026-09). 2.1 환경에서는 "PAIS 3.0부터"로 표기한 대목만 건너뛰면 됩니다. 적용 전 최신 공식 문서로 재확인하시기 바랍니다.

---

## 13.1 평가가 어려운 이유

에이전트의 출력은 결정적이지 않습니다. 같은 입력에도 표현이 달라지고, 검색과 도구 호출의 경로가 입력에 따라 바뀝니다. 그래서 "정확히 이 문자열을 반환한다"는 단언적 테스트가 잘 들어맞지 않습니다. 평가는 **단일 통과/실패가 아니라 분포와 경향**으로 봐야 하며, 대표 입력 묶음에 대한 반복 측정이 필요합니다.

## 13.2 PAIS가 제공하는 것 — 그리고 제공하지 않는 것

- **Playground(대화형 테스트)** — Agent Builder에 내장된 1차 검증 수단입니다. 사람이 직접 대화하며 검색, 도구 호출, 거절 동작을 눈으로 확인하고 지시문을 수정과 보완합니다([08 8.7절](08-agent-builder.md)).
- **CI/CD 자동 테스트** — 공식 문서가 명시하는 것은 Playground와 구성 코드 보기(View Configuration Code)까지입니다([근거: Create an Agent for a Generative AI Application](https://techdocs.broadcom.com/us/en/vmware-cis/private-ai/foundation-with-nvidia/9-0/private-ai-foundation-9-x/what-is-private-ai-services/deploy-an-agent-for-a-rag-application.html)). 그 구성 코드를 형상관리에 두고([08 8.8절](08-agent-builder.md)) 파이프라인에서 대표 입력으로 에이전트를 호출해 회귀를 잡는 자동 테스트는 이 가이드가 권하는 실무 패턴입니다.

> **분명히 해 둘 경계** — PAIS에 이름 붙은 전용 평가(eval) 스코어링 프레임워크가 있다는 공식 근거는 확인되지 않습니다. 따라서 정량 평가 묶음(테스트셋, 채점 기준, 회귀 추적)은 **애플리케이션과 CI 계층에서 직접 설계**해야 합니다. Playground는 탐색적 1차 검증, CI는 반복 검증으로 역할을 나누십시오.

## 13.3 무엇을 측정하나

대표 입력 묶음을 정해 다음을 반복 측정하십시오.

| 측정 대상 | 무엇을 보나 |
|-----------|-------------|
| 검색 적절성 | 필요한 때 검색하는가, 검색어, Top-K, 컷오프가 맞는가 |
| 도구 선택 정확도 | 올바른 도구를 부르는가, 인자가 맞는가 |
| 근거성(환각 여부) | 답이 검색과 도구 결과에 근거하는가, 인용이 맞는가 |
| 종단 품질 | 최종 답이 과업을 실제로 해결하는가 |
| 비용과 지연 | 토큰, 단계 수, TTFT, 종단 지연이 허용 범위인가([14](14-operations.md)) |

지시문, 검색 파라미터, 모델을 바꿀 때마다 이 묶음을 다시 돌려 **회귀**를 확인하십시오. 한 입력에서 좋아진 변경이 다른 입력을 망치는 일이 흔합니다.

## 13.4 실패 유형

에이전트에는 단일 호출에 없던 실패가 생깁니다.

- **환각(근거 없는 단정)** — 검색과 도구 결과 없이 그럴듯한 답을 지어냅니다. 인용 표시와 근거성 평가와 함께, "모르면 모른다고 답하라"는 규칙을 지시문에 넣어 줄입니다.
- **도구 오선택** — 비슷한 도구를 잘못 고르거나 인자를 틀립니다. 도구 수를 줄이고 이름과 설명을 명확히 하면 줄어듭니다([03 3.3절](03-design-patterns.md)).
- **루프** — 같은 검색과 도구 호출을 반복하며 끝내지 못합니다. 최대 단계와 시간 한계로 종료 조건을 둡니다.
- **권한 초과** — 의도 밖 시스템에 쓰기와 전송을 시도합니다. 도구 권한 최소화와 승인 통제로 막습니다([09 9.7절](09-mcp-tools.md)).

## 13.5 가드레일 — PAIS의 한계와 보완

"가드레일"이라는 말은 PAIS 맥락에서는 인프라 관점에서 두 가지 의미로 주로 쓰입니다.

- **리소스 가드레일** — 격리된 vSphere Namespace의 CPU, 메모리, GPU 쿼터. 한 워크로드가 자원을 독식하지 못하게 막는 운영 통제입니다.
- **거버넌스 포지셔닝** — 에이전트 루프와 도구 사용에 대한 상위 플랫폼 차원의 거버넌스 방향.

> **분명히 해 둘 경계** — 콘텐츠 모더레이션과 프롬프트 인젝션 방어 같은 **PAIS 내장 콘텐츠 가드레일**은 없으며, 그 경계 선언과 어떤 가드를 어디에 두고 무엇으로 만드는지의 선택과 배치는 [12 12.3절](12-service-security.md)이 정본입니다. 이 절은 그 한계를 **평가 관점**에서 다룹니다 — 입력과 출력 필터, 도구 권한 최소화, 승인 통제([09](09-mcp-tools.md)), 지시문의 거절 규칙이 골든셋과 회귀로 실제 동작하는지를 확인하는 것이 이 절의 몫입니다. 플랫폼 정책과 통제 상세는 [⑤ 앱 계층 가드레일](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/06-app-guardrails.md)이 다룹니다.

**원격 클라우드 모델을 쓰는 에이전트의 추가 가드레일(PAIS 3.0부터)** — 에이전트의 completion 엔드포인트가 원격 클라우드 모델이면([10 10.1절](10-models-serving.md)), 위에서 앱 계층이 맡는 입출력 필터에 한 층이 더 필요합니다. 프롬프트에 실리는 검색 청크와 도구 결과가 사외로 나가기 때문입니다. 그래서 원격 모델 에이전트에는 연결할 수 있는 지식베이스와 도구를 반출 정책이 허용한 것으로 제한하고, 도구 결과가 프롬프트에 들어가기 전에 PII 마스킹을 거치게 하며, 평가 골든셋에 "기밀 등급 문서를 근거로 답해야 하는 질문"을 넣어 그런 질문이 원격 모델 에이전트로 흘러가지 않는지를 회귀로 확인합니다. 어떤 데이터가 나가도 되는지의 기준은 [⑤ 데이터 거버넌스 5.6절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/05-data-governance.md)이 정합니다.

**플랫폼이 이 영역을 흡수할 가능성** — 2026-08 Explore에서 에이전트 코드 샌드박스와 도구 접근을 통제하는 Agent Harness로 이뤄진 Secure Agent Framework가 발표됐습니다. PAIS 3.0 릴리스 노트에는 없는 향후 기능이므로 이 절의 앱 계층 책임 구분은 그대로이고, 상태는 [00 0.6절](00-orientation.md)에서 추적합니다. 이미 GA된 것으로는 에이전트 신원과 도구 호출 게이트웨이를 제공하는 별도 제품 AgentMinder(2026-08-31)가 있으며, PAIS 구성요소가 아니므로 에이전트에서 도구로 가는 경로에 정책 집행 계층을 둘지의 결정([⑤ 08 8.8절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/08-agent-governance.md))에서 선택지의 하나로 다룹니다. 에이전트를 행위자로 보는 위협 목록과 자율성 상한, 레지스트리, 도구 오염 통제의 정본은 [⑤ 08](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/08-agent-governance.md)이고, 이 서비스에 대입하는 점검표는 [12 12.4절](12-service-security.md)입니다.

## 13.6 휴먼인더루프 — 검증 관점의 점검

되돌리기 어려운 행동(쓰기, 전송, 결제, 구성 변경) 앞에 사람의 확인을 두는 것은 에이전트 안전의 핵심입니다. PAIS에 런타임 응답을 사람이 승인하거나 차단하는 내장 휴먼인더루프 기능은 확인되지 않으며, MCP 도구의 "승인"은 도구 등록을 통제하는 절차이지 매 호출의 승인이 아닙니다([09 9.4절](09-mcp-tools.md)). 따라서 승인 게이트는 애플리케이션 계층에서 구현합니다. 세 패턴(제안 후 승인, 대기 큐, 드라이런)과 승인 큐의 상태 기계, 작업 분류표는 설계 편 [07 7.2절과 7.3절](07-integration-write-design.md)이 정본입니다.

검증 단계에서 점검할 것은 설계가 실제로 지켜졌는가입니다.

- 작업 분류표의 "승인 필수" 작업이 승인 없이 실행되는 경로가 없는가. 골든셋에 "승인 없이 전송을 시도하는 입력"을 넣어 회귀로 확인합니다.
- 승인 만료와 대상 변경(승인 뒤 티켓이 이미 닫힘) 시 실행하지 않는가.
- 킬스위치가 서비스 단위로 동작하고, 켜졌을 때 대기 중인 작업이 보류되는가.
- 승인 화면에 근거가 함께 보여 승인 피로를 만들지 않는가.

이 경계를 분명히 알고 설계하면, "에이전트가 알아서 다 한다"는 위험한 기대 대신 **통제 가능한 자동화**를 만들 수 있습니다.

## 13.7 평가 방법 — 골든셋, 채점, 회귀, 피드백 루프

13.3절이 무엇을 측정하는지였다면, 여기서는 어떻게 평가 체계를 만드는지를 다룹니다. PAIS에 전용 평가 프레임워크가 없으므로(13.2절), 이 체계는 앱과 CI 계층에서 직접 만듭니다.

- **골든셋** — 대표 입력과 기대 동작을 묶은 평가용 데이터셋입니다. 실제 사용 사례, 과거 실패, 경계 사례를 모으고, 각 항목에 기대 답, 기대 도구 호출, 기대 검색을 적어 둡니다. 처음에는 수십 개로 작게 시작해 운영하며 키웁니다.
- **채점** — 항목별로 통과와 실패를 정합니다. 정형 동작(도구 호출, 인자, 검색 여부)은 규칙으로 자동 채점하고, 자유 서술 답의 품질은 **LLM 채점(LLM-as-judge)** — 별도 모델에 채점 기준을 주어 점수를 매기는 방식 — 으로 보완합니다. LLM 채점은 편향이 있으니 일부를 사람이 표본 검수해 보정합니다.
- **회귀와 게이트** — 지시문, 모델, 파라미터를 바꿀 때마다 골든셋을 다시 돌려 점수를 비교합니다(13.3절). 합격선(예: 핵심 항목 전부 통과, 전체 점수 하락 없음)을 정해 CI 게이트로 걸면, 한 변경이 다른 입력을 망치는 회귀를 배포 전에 잡습니다([08 8.8절](08-agent-builder.md) 구성 코드와 CI).
- **A/B 비교** — 두 구성(모델과 지시문)을 같은 골든셋으로 나란히 채점해 어느 쪽이 나은지 정량 비교합니다. 운영 트래픽으로 비교한다면 사용자 영향을 통제하며 일부에만 노출합니다(트래픽 분할과 램프업은 13.9절).

**온라인 피드백 루프** — 출시 전 평가(이 절)와 운영 관측([14 14.2절](14-operations.md))은 끊겨 있으면 안 됩니다. 운영 추적에서 드러난 실패, 약한 답을 골든셋에 더해 회귀 묶음을 키우면, 평가가 실사용을 따라 진화합니다. 이 피드백 루프가 품질 드리프트(시간이 지나며 품질이 조금씩 떨어지는 현상)를 잡는 핵심입니다.

## 13.8 프롬프트 수명주기 — 프롬프트를 1급 자산으로

모델은 리비전과 다이제스트로 관리되는데 프롬프트는 채팅창에 붙여 넣은 문자열로 남아 있는 서비스가 많습니다. 에이전트의 동작은 지시문, 시스템 프롬프트, 도구 설명, 출력 스키마가 모델만큼 좌우하므로, 이것들도 모델과 같은 수명주기를 가져야 합니다.

- **레지스트리** — 프롬프트 자산(지시문, 시스템 프롬프트, 도구 설명, 출력 스키마, 폴백 문구)을 버전, 해시, 소유자, 변경 사유와 함께 보관합니다. 첫 레지스트리는 Git이면 충분하며, Agent Builder의 구성 코드([08 8.8절](08-agent-builder.md))를 형상관리에 두는 것이 그 출발점입니다. 프롬프트 수가 늘어 팀 간 공유가 필요해지면 이너소스 저장소([05 5.6절](05-platform-consumption.md))로 올립니다.
- **조합 핀닝** — 프롬프트 버전, 모델 리비전, 추론 파라미터(temperature, max_tokens), 도구 목록은 한 묶음으로 검증됩니다. 어느 하나만 바꿔도 회귀 대상이며, "프롬프트는 그대로인데 모델이 바뀌어 답이 달라진" 사고는 이 묶음을 기록하지 않아서 생깁니다. 묶음의 기록이 13.9절의 릴리스 매니페스트입니다.
- **프롬프트 단독 릴리스** — 모델을 다시 배포하지 않고 프롬프트만 바꾸는 경로를 앱에 둡니다(앱이 시작 시 또는 주기적으로 레지스트리에서 읽음). 배포가 가벼워지는 만큼 통제도 가벼워지기 쉬우므로, 프롬프트만 바뀌어도 골든셋 회귀와 카나리 노출은 같은 규칙으로 요구합니다. 시스템 프롬프트와 가드레일 정책의 버전 관리는 [⑤ 06 6.6절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/06-app-guardrails.md)의 요구이기도 합니다.
- **환경별 승격** — 개발, 스테이징, 프로덕션 순으로 승격하며 단계마다 평가 게이트를 둡니다. PAIS 3.0부터 지식베이스와 인덱스를 복제할 수 있으므로, 복제본에 연결한 스테이징 에이전트에서 프롬프트와 모델 변경을 먼저 검증하고 승격하는 흐름이 가능합니다([14 14.7절](14-operations.md)). 플랫폼 쪽 모델 수명주기(버전, 평가, 승격, 롤백, 재학습)는 [① 06 6.7절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/01-infra/docs/06-production.md)에 있고, 이 절은 그 순환에 프롬프트를 얹은 것입니다.

## 13.9 릴리스 매니페스트와 A/B 트래픽 분할

**릴리스 매니페스트**는 서비스의 한 릴리스가 정확히 무엇으로 이뤄졌는지를 한 장에 적은 기록입니다. 사고 조사에서 "그때 어떤 프롬프트와 모델이었나"에 답하고, 규제가 요구하는 문서 보존의 뼈대가 되며, 롤백 대상을 명확히 합니다.

| 필드 | 내용 | 출처 |
|------|------|------|
| 서비스와 릴리스 버전 | 서비스 ID, 릴리스 번호, 배포 일시, 승인자 | 레지스트리 |
| 모델 | 엔드포인트 이름, 모델 리비전 다이제스트, 로컬 또는 공유 또는 원격 여부 | Model Gallery Revision([10 10.3절](10-models-serving.md)) |
| 서빙 엔진 | 엔진과 버전(예: vLLM 0.20.0), 양자화 포맷 | [10 10.2절](10-models-serving.md) |
| 프롬프트 | 지시문과 시스템 프롬프트와 출력 스키마의 버전과 해시 | 13.8절 레지스트리 |
| 추론 파라미터 | temperature, max_tokens, 도구 호출 설정 | 구성 코드 |
| 도구 | 도구 목록, MCP 서버 버전, 승인 시점의 도구 설명 해시 | [09 9.7절](09-mcp-tools.md) |
| 지식베이스 | 지식베이스 ID, 인덱스 버전, 임베딩 모델과 리비전, 청킹 설정 | [06](06-data-onboarding.md) |
| 가드레일 | 입력과 출력 가드의 정책 버전과 가드 모델 리비전 | [12 12.3절](12-service-security.md) |
| 평가 | 골든셋 버전, 점수, 합격선, 회귀 결과 | 13.7절 |
| 레드팀 | 실행일, 도구, 임계값 통과 여부, 면제 목록 | [12 12.6절](12-service-security.md) |
| 라이선스 | 모델과 부속 모델의 라이선스 심사 결과 참조 | [10 10.8절](10-models-serving.md) |

매니페스트는 사람이 손으로 쓰지 않고 CI가 생성하도록 합니다. 구성 코드, 골든셋 결과, 레지스트리에서 값을 모아 릴리스마다 한 파일로 남기고, 서비스 레지스트리([⑤ 08 8.4절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/08-agent-governance.md))의 현재 릴리스 필드가 이 파일을 가리키게 합니다.

**A/B 트래픽 분할** — 골든셋 비교(13.7절)가 오프라인이라면, 운영 트래픽의 일부에 새 구성을 노출해 실사용 지표로 비교하는 것이 A/B입니다. 정할 것은 넷입니다.

1. **분할 위치** — BFF 또는 1계층 AI 게이트웨이의 가중 라우팅([05 5.2절](05-platform-consumption.md)). 같은 사용자는 세션 동안 같은 구성을 보도록 고정합니다.
2. **램프업** — 소수 비율에서 시작해 단계적으로 늘리며(예: 1%, 10%, 50%), 단계마다 되돌림 조건(오류율, 지연, 채택률 하락)을 정합니다.
3. **비교 지표와 표본** — 채택률, 피드백 점수([11 11.5절](11-app-integration-ux.md)), 지연, 비용. 차이가 우연이 아니라고 말하려면 필요한 표본 수를 미리 계산하고, 그 전에는 결론을 내리지 않습니다.
4. **기록** — 두 구성 모두 매니페스트로 남기고, 승자의 승격은 13.8절의 환경별 승격 규칙을 따릅니다.

## 13.10 출시 심사 패키지

출시 심사는 앞 장들의 결과를 한 묶음으로 모아 심사 주체([⑦ 09 9.2.1절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/07-design/docs/09-roles-raci.md)의 AI 위험관리 책임자, 보안, 법무)에게 제출하는 절차입니다. 패키지의 구성은 위험 등급과 무관하게 같고, 등급이 낮으면 각 항목이 짧아질 뿐입니다.

| 항목 | 내용 | 출처 |
|------|------|------|
| 유스케이스 정의 | 목적, 대상 사용자, 위험 등급과 판정 근거, 자율성 상한, 조회 전용 여부 | [02 2.9절, 2.10절, 2.11절](02-use-cases.md) |
| 신원과 권한 | 신원 전파 패턴, 검색 필터와 도구 권한의 근거, 감사 필드 | [04](04-identity-propagation.md) |
| 데이터 소스 | 소스별 승인서와 등급, 보호 문서 인입 방식, 개인정보 영향평가 검토 결과 | [06 6.9절](06-data-onboarding.md) |
| 쓰기 작업 | 작업 분류표, 승인 게이트 설계, 멱등과 보상 검증 결과 | [07](07-integration-write-design.md) |
| 릴리스 매니페스트 | 13.9절의 전체 필드 | 13.9절 |
| 평가 결과 | 골든셋 점수와 합격선, 회귀 결과, A/B 결과가 있으면 함께 | 13.7절 |
| 보안 준비 | 가드레일 배치, 에이전트 위협 점검표, 레드팀 결과, 면제 목록과 만료일, 게이트 체크리스트 | [12](12-service-security.md) |
| 신뢰 UX와 고지 | 출처 표시와 폴백 설계, AI 생성 고지 문안과 배치, 대화 데이터 보존과 열람 삭제 경로 | [11 11.3절, 11.6절, 11.7절](11-app-integration-ux.md) |
| 운영 준비 | SLO, 알람, 온콜, 롤백 절차, 킬스위치, 플랫폼 SLA 확인 | [14 14.8절, 14.11절](14-operations.md) |
| 법무 확인 | 모델 라이선스 심사 결과, 고영향 AI 해당 여부 판정, 표시 의무 적용 범위 | [10 10.8절](10-models-serving.md), 법무 검토 기록 |

**규제가 요구하는 문서 보존** — 인공지능기본법은 고영향 AI에 위험관리방안과 이행 문서의 보관을 요구하고, 금융분야 인공지능 가이드라인은 위험 등급별 출시 심사와 위험관리 조직의 독립을 요구합니다. 이 패키지가 그 문서의 뼈대가 되도록, 심사 결과와 승인 기록을 릴리스마다 보존하고 보존 기간은 [⑤ 07 7.1.3절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/07-audit-compliance.md)의 정책을 따릅니다. 어느 서비스가 고영향에 해당하는지와 시행 일정은 [AX 방법론 부록 A2](https://github.com/JaeHoYun/enterprise-ax-methodology/blob/main/appendix/A2-kr-regulatory-timeline.md)를 단일 출처로 삼고 법무 검토로 확정합니다. 내부 전용 서비스라도 같은 패키지를 가볍게 만들어 두면, 나중에 대외로 확장하거나 등급이 오를 때 처음부터 다시 쓰지 않아도 됩니다.
