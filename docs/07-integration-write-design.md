# 07 — 사내 시스템 연동과 쓰기 설계

[← 목차로](../README.md)

서비스가 사내 시스템을 읽기만 하는 동안은 실패해도 답이 틀릴 뿐입니다. 쓰기를 시작하는 순간 실패는 부작용이 됩니다 — 티켓이 두 번 생기고, 레코드가 반쯤 바뀌고, 메시지가 잘못 나갑니다. 이 문서는 사내 시스템 연동을 읽기와 쓰기로 나눠, 연동 방식 선택, 작업 분류, 승인 게이트, 정합성(멱등과 보상), 다운스트림 보호, 데이터 계약을 설계하는 방법을 다룹니다. 안전 축(승인)과 정합성 축(멱등, 보상)을 함께 갖춰야 쓰기 연동이 완결됩니다.

> 본 문서의 수치와 동작은 VCF 9.1.1 / PAIF 9.1.1 / PAIS 3.0 기준입니다(작성 2026-09). PAIS에 런타임 응답을 사람이 승인하는 내장 휴먼인더루프 기능은 확인되지 않으므로, 이 문서의 승인 게이트는 애플리케이션 계층 설계입니다. 적용 전 최신 공식 문서로 재확인하시기 바랍니다.

---

## 7.1 연동 방식 선택 — API, MCP, RPA

사내 시스템에 닿는 길은 셋입니다. 선택 기준은 "누가 호출하는가"와 "시스템에 API가 있는가"입니다.

| 방식 | 무엇 | 적합 | 주의 |
|------|------|------|------|
| **앱이 직접 API 호출** | 앱(BFF나 오케스트레이션 계층)이 사내 시스템의 REST나 메시지 API를 부름 | 사용자 범위 권한이 필요한 읽기와 모든 쓰기([04 4.3절](04-identity-propagation.md) 패턴 B) | 연동 코드는 앱 팀 자산. 도구 정의를 모델에 노출하지 않으므로 모델이 임의로 부르지 못함 |
| **MCP 도구** | 사내 시스템을 MCP 서버로 감싸 에이전트가 판단해 호출([09](09-mcp-tools.md)) | 입력마다 어느 시스템을 조회할지 달라지는 읽기. 공식이나 커뮤니티 MCP 서버가 있는 시스템 | 관리형 경로에서는 정적 토큰 하나로 호출되므로 서비스 범위 도구만([04 4.4절](04-identity-propagation.md)). 쓰기 도구는 승인 게이트 뒤에 |
| **RPA와 화면 자동화** | API가 없는 레거시를 화면 조작으로 다룸 | API를 만들 수 없는 시스템의 마지막 수단 | 화면이 바뀌면 깨지고 감사 근거가 약함. 에이전트에 RPA를 붙여 "에이전트"라 부르는 것은 [02 2.2절](02-use-cases.md)의 에이전트 워싱 |

레거시에 API가 없고 담당자가 없는 상태는 그 자체가 연동 준비도 부채입니다([AX 03 3.6절](https://github.com/JaeHoYun/enterprise-ax-methodology/blob/main/docs/03-problem-definition.md)). 이런 시스템은 첫 서비스의 연동 대상에서 빼고, 읽기 전용 API를 먼저 만드는 것을 별도 과제로 둡니다.

## 7.2 작업 분류표 — 되돌리기 어려움과 영향 범위

쓰기 설계의 출발점은 서비스가 사내 시스템에 하는 모든 작업을 분류하는 것입니다. 기준은 두 가지, 되돌리기 어려움과 영향 범위입니다.

| 작업 유형 | 예 | 되돌리기 | 기본 통제 |
|-----------|----|----------|-----------|
| 조회 | 티켓 검색, 재고 조회, 로그 읽기 | 해당 없음 | 자동. 권한 범위와 감사 로그만 |
| 생성 | 티켓 생성, 초안 저장 | 삭제로 되돌림 | 멱등 키 필수. 위험 등급 중간 이상이면 승인 |
| 변경 | 레코드 갱신, 상태 전환 | 이전 값 복원 | 승인 + 변경 전 값 기록 |
| 전송 | 메일과 메시지 발송, 외부 API 호출 | 되돌릴 수 없음 | 승인 필수. 드라이런으로 내용 확인 |
| 결제와 삭제 | 결제, 레코드 삭제, 구성 변경 | 되돌릴 수 없거나 비용 큼 | 승인 필수. 첫 배치에서는 제외 |

이 표의 결과가 [02 2.9절](02-use-cases.md)의 위험 등급 판정에서 "쓰기 권한이 있는가" 질문의 답이 됩니다. 첫 서비스는 조회와 생성까지로 한정하고, 전송 이상은 사람이 실행하는 것이 [02 2.10절](02-use-cases.md)의 자율성 상한 L1과 같은 말입니다.

## 7.3 승인 게이트 — 휴먼인더루프 세 패턴과 승인 큐

되돌리기 어려운 행동 앞에 사람의 확인을 두는 것은 에이전트 안전의 핵심입니다. PAIS의 MCP 도구 "승인"은 관리자가 **도구 등록을 통제**하는 절차이지 매 호출을 사람이 승인하는 것이 아니므로([09 9.4절](09-mcp-tools.md)), 호출 단위 승인 게이트는 앱이 만듭니다. 구현 패턴은 셋입니다.

- **제안 후 승인(propose-then-approve)** — 에이전트는 위험한 행동을 직접 실행하지 않고 제안만 만들고, 사람이 승인하면 그때 앱이 실제 작업을 호출합니다. 가장 단순하고 안전한 기본형이며, 사례 A의 "티켓 생성"과 사례 B의 "초안까지만"이 이 모습입니다([02](02-use-cases.md)).
- **대기 큐(pending state)** — 위험 행동을 대기 상태로 큐에 쌓고, 사람이 검토, 승인, 반려할 때까지 실행을 보류합니다. 비동기와 다건 승인에 맞습니다.
- **드라이런(dry-run)** — 실제로 바꾸지 않고 "무엇을 할지"만 시뮬레이션해 보여 준 뒤 확인을 받고 본 실행합니다. 구성 변경과 대량 작업에 유용합니다.

패턴 이름만으로는 운영이 되지 않습니다. 승인 큐를 만들 때 정해야 하는 것은 다음 상태 기계입니다.

| 요소 | 정할 것 |
|------|---------|
| 상태 | 제안됨 → 검토 중 → 승인됨 → 실행 중 → 완료 / 반려됨 / 만료됨 / 실행 실패 |
| 승인자 | 작업 유형과 영향 범위에 따라 누가 승인하는가. 요청자와 승인자의 직무 분리 |
| SLA와 만료 | 승인 대기 시간 상한. 만료되면 자동 반려하고 요청자에게 알림. 만료된 제안을 뒤늦게 실행하지 않음 |
| 실행 조건 | 승인 시점과 실행 시점 사이에 대상이 바뀌었으면(예: 티켓이 이미 닫힘) 실행하지 않고 재검토 |
| 감사 필드 | 제안 내용, 제안 근거(에이전트 세션과 요청 ID), 승인자, 승인 시각, 실행 결과, 변경 전 값 |
| 킬스위치 | 서비스 단위로 모든 쓰기를 즉시 보류하는 스위치. 사고 대응의 첫 조치 |

승인 화면은 제안 내용을 사람이 읽고 판단할 수 있게 근거(검색한 문서, 조회한 레코드)를 함께 보여 줍니다. 근거 없는 승인 요청은 "승인 피로"를 낳아 사람이 무조건 승인하게 만듭니다.

## 7.4 정합성 — 멱등 키, 보상, 트랜잭션 경계

승인이 안전 축이라면 정합성은 "한 번 실행한 것이 정확히 한 번만 반영되고, 중간에 실패하면 알려진 상태로 돌아가는" 축입니다. 에이전트는 재시도와 다단계 때문에 이 축이 특히 약합니다.

**멱등 키 규약**

- **누가 만드나** — 앱(BFF 또는 오케스트레이션 계층)이 사용자 요청 하나에 요청 ID를 만들고, 그 요청에서 파생되는 쓰기 작업마다 "요청 ID + 작업 순번"으로 멱등 키를 만듭니다. 모델이 생성한 값을 멱등 키로 쓰지 않습니다. 재시도 때 모델이 다른 값을 만들면 중복 실행이 됩니다.
- **어디에 저장하나** — 앱의 작업 저장소에 멱등 키와 결과를 함께 저장하고, 같은 키의 요청이 오면 실행 대신 저장된 결과를 돌려줍니다. 대상 시스템이 멱등 키 헤더를 지원하면 그 헤더로도 전달합니다.
- **재시도 윈도우와 TTL** — 재시도가 허용되는 시간 창(예: 승인 SLA와 같은 길이)을 정하고, 그 밖의 같은 키 요청은 거부합니다. 키의 보존 기간은 감사 요건에 맞춥니다.

**다단계 실패의 보상 매트릭스**

에이전트가 세 시스템에 차례로 쓰다가 두 번째에서 실패하면 첫 번째는 이미 반영된 상태입니다. 분산 트랜잭션은 사내 시스템 사이에서 기대할 수 없으므로, 단계마다 보상 행동을 미리 정합니다.

| 단계 | 정방향 작업 | 실패 시 보상 | 보상이 불가능하면 |
|------|-------------|--------------|-------------------|
| 1 | 티켓 생성 | 티켓 취소 또는 "자동 생성 실패" 상태로 표시 | — |
| 2 | 레코드 갱신 | 변경 전 값으로 복원(7.3절의 변경 전 값 기록이 근거) | 사람에게 상신하고 작업을 실패 상태로 |
| 3 | 알림 전송 | 되돌릴 수 없음. 정정 알림 전송 | 마지막 단계에 두어 앞 단계가 모두 성공한 뒤에만 실행 |

원칙은 세 가지입니다. 되돌릴 수 없는 작업은 순서의 맨 뒤에 둡니다. 각 단계의 성공 여부를 작업 저장소에 기록해 재시작이 중간부터 가능하게 합니다. 보상이 실패하면 자동으로 더 시도하지 않고 사람에게 넘깁니다.

**트랜잭션 경계** — 한 사내 시스템 안에서 원자적으로 처리해야 하는 작업은 그 시스템의 API 하나로 묶어 요청합니다. 에이전트가 여러 번의 API 호출로 하나의 업무 트랜잭션을 조립하게 두면 중간 상태가 노출됩니다.

## 7.5 다운스트림 보호 — 레거시가 병목일 때

에이전트의 도구 호출은 루프와 다단계로 늘어나며, 배치 파이프라인은 대량 호출을 만듭니다. 도구 서버를 확장해도 그 뒤의 레거시 시스템은 늘어나지 않습니다.

- **동시성 상한** — 사내 시스템별로 동시 호출 수 상한을 앱이 지킵니다. 도구 서버나 앱의 호출 계층에 세마포어를 두고, 상한을 넘는 요청은 큐잉합니다.
- **레이트리밋과 백프레셔** — 대상 시스템이 429나 지연으로 신호를 보내면 지수 백오프로 물러납니다. 에이전트 루프 안에서 같은 도구를 연속 호출하는 것은 단계 상한으로 막습니다([03 3.5절](03-design-patterns.md)).
- **쿼터 배분** — 여러 서비스가 같은 사내 시스템을 부르면 서비스별 쿼터를 정해 한 서비스의 폭주가 다른 서비스를 막지 않게 합니다. 배치는 온라인 서비스와 다른 시간대나 다른 쿼터로 돌립니다([03 3.7절](03-design-patterns.md)).
- **캐시** — 조회 결과 중 자주 바뀌지 않는 것(마스터 데이터, 조직도)은 앱이 짧은 TTL로 캐시해 레거시 호출을 줄입니다. 사용자 범위 데이터는 사용자 단위로 캐시하거나 캐시하지 않습니다.

## 7.6 데이터 계약 — 도구 스키마의 버전

에이전트가 도구를 고르고 인자를 채우는 근거는 도구의 이름, 설명, 입출력 스키마입니다. 이것이 바뀌면 에이전트의 동작이 바뀝니다.

- **버전을 붙입니다** — 도구 스키마에 버전을 두고, 하위 호환이 깨지는 변경(필수 인자 추가, 의미 변경)은 새 도구로 등록합니다. 기존 도구는 이전 기간 뒤 폐기합니다.
- **변경은 회귀 평가를 거칩니다** — 스키마 변경 뒤 골든셋을 다시 돌려 도구 선택 정확도와 인자 정확도를 확인합니다([13 13.7절](13-evaluation-guardrails.md)).
- **설명은 코드처럼 검토합니다** — 도구 설명은 모델이 읽는 지시문입니다. 등록 시점의 설명을 해시로 기록해 두고, 도구 서버가 설명을 바꾸면 자동 승인 상태를 해제하고 재검토합니다. 승인 뒤 바뀐 도구 설명으로 에이전트를 조종하는 공격이 알려져 있습니다(검증 편의 서비스 보안 준비에서 이어 다룹니다).

## 7.7 도구 반환값은 신뢰하지 않는다

도구가 돌려주는 내용(티켓 본문, 문서 텍스트, 외부 API 응답)은 사용자 입력과 같은 비신뢰 데이터입니다. 그 안에 "다음 지시를 따르라"는 문장이 있어도 모델이 따라서는 안 됩니다. 도구 결과를 프롬프트에 넣기 전에 살균하고, 도구 결과가 다른 도구 호출을 유도하는 구조(예: 조회 결과에 든 지시로 전송 도구를 부름)는 승인 게이트 없이는 허용하지 않습니다. 원칙은 [⑤ 06 6.4절](https://github.com/JaeHoYun/vcf-private-ai/blob/main/05-security/docs/06-app-guardrails.md)이 정하고, 가드레일의 선택과 배치는 검증 편에서 다룹니다.

## 7.8 결정 기록

서비스 설계 문서에 다음을 남깁니다.

1. 연동 대상 시스템 목록과 각각의 연동 방식(API, MCP, RPA)과 그 이유.
2. 작업 분류표(7.2절)와 각 작업의 통제(자동, 멱등, 승인, 제외).
3. 승인 큐의 상태 기계, 승인자, SLA, 킬스위치 위치.
4. 멱등 키 규약과 작업 저장소, 보상 매트릭스.
5. 사내 시스템별 동시성 상한과 쿼터.
6. 도구 스키마 버전과 변경 절차.
